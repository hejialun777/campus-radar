# 校园机会雷达

> 项目一 · 对应考核材料第四部分「校园活动与机会信息」
> 在线体验：`https://<用户名>.github.io/<仓库名>/projects/campus-radar/`

---

## 一、产品名称

**校园机会雷达** —— 一个面向在校学生、重点照顾新生的校园活动与机会聚合产品。

## 二、主要解决的问题

题目给了 26 条来源不同、格式不同、质量不一的校园信息。真实校园里也是这个样子：
活动分散在学院通知、社团群、朋友圈和同学口口相传里。真正的问题不是"信息太少"，
而是下面这四件事：

1. **同一件事有好几条通知，得自己判断哪条更新。**
   材料里 09 是 01 的场地变更通知，20 是 03 的名额变更说明。散着看很容易按旧信息行动。

2. **不知道这件事现在是什么状态。**
   "9月24日22:00截止"这句话，只有在知道今天几号的前提下才有意义。
   材料里同时存在今天就要开始的、明天中午就截止的、报名早就过了的、已经结束等回放的。

3. **通知写得不清不楚，但没人告诉你哪里不清楚。**
   06 没写报名截止时间，14 没写预约截止时间还说"填表不等于录取"，
   12 没说要不要交钱，22 说"场地待最终确认"。这些缺口比信息本身更值得提醒。

4. **不是所有信息都值得信。**
   24、25 是学生发布里明显的信息残缺和疑似推广内容。全删掉会伤害开放发布，
   直接展示又不负责。

## 三、核心功能

### 1. 后续通知自动合并

材料里的 09、20 不再作为独立条目出现，而是挂到主信息（01、03）上：

- 列表里 26 条信息变成 **24 条**，同一件事只出现一次；
- 卡片上标「已合并 1 条后续通知」，点开能看到完整的变更记录；
- 活动时间直接采用最新通知的结果：01 的首次训练显示为
  **9月21日(周一) 19:30 · 实验楼A402**，而不是原来那条作废的时间；
- 合并后仍保留两条通知的**原文**，可追溯、可核对。

### 2. 按"现在"推算状态

以当前时间为基准，自动把每条信息判成：正在进行 / 今天开始 / 快到截止时间了 /
还能报名 / 报名已截止可候补 / 已结束待回放 / 长期开放。

列表按这个状态分组排序，最上面永远是"我现在能做什么"。
同一个产品在 9 月 19 日、9 月 20 日、9 月 25 日打开，呈现的重点完全不同。

### 3. 不确定的信息如实标注，不编造

- 通知没写的字段一律留空，显示为「未注明」，并列出具体缺了哪几项；
- 每条信息有一个**信息完整度**（6 项关键字段里提供了几项）；
- 「我要做什么」把字段翻译成动作，缺什么就提示去确认什么
  （"地点还没定，出发前记得再确认一次"）。

### 4. 新生模式

一键筛掉新生参加不了的（13 号"仅限大二及以上"），并给每条信息标注新生适配度：

- ✅ 零基础可参加 / 新生友好·直接去
- ⚠️ 未说明基础要求 / 信息不明需先确认
- ⛔ 新生暂不符合

### 5. 学生自主发布

同学可以发约球、找搭子、组队这类信息。两个关键设计：

- **发布时实时自检**：边填边提示"还有 地点、费用 没填，同学看到之后还得再来问你一次"；
- **发布后进入正常流程**：和官方信息一起参与筛选、搜索、排序，
  但会标注「学生发布 · 未核实」，信息不全的自动附上风险提示。

### 6. 收藏 / 已参加 / 我的日程

所有操作存 `localStorage`，刷新、关页面、重新打开都还在。

## 四、自主设计的实用与创新功能

### 一键加入手机日历（.ics 导出）

详情页可以把这个活动导出成 `.ics` 文件，手机点开就进系统日历，自带提前两小时提醒。

选它是因为：活动信息最实际的落地动作就是"到点出现在我手机上"。
26 条信息里有明确时间的占大多数，学生真正会漏掉的是**明天中午 12:00 截止**这种，
而不是"没看到过这条信息"。把提醒交给系统日历，比让用户记住更可靠。

### 信息完整度计量

不是主观打分，而是机械地检查 6 个对学生决策最关键的事实字段是否提供：
时间、地点、面向对象、是否需报名、报名截止、费用。

这样"来源不同、质量不一"就不再是一句感觉，而是一个可比较的数字；
配合详情页的"缺哪几项 + 该去确认什么"，把信息质量问题变成了可操作的动作。

## 五、主动发现并处理的关键问题

**问题：材料里的"更新时间"和"活动时间"是两回事，混在一起会误导用户。**

材料里至少有三处是这样的：

| 条目 | 表面信息 | 实际问题 |
| --- | --- | --- |
| 17 | "资料长期开放" | 但"当前网盘提取信息有效至9月22日"——资料长期开放不等于现在这份提取码长期有效。从 9/19 算只剩 3 天，是全部信息里第三紧急的 |
| 04 | "数学建模经验分享会" | 直播 9/18 已结束，但"9月20日上传回放"——它不是一条过期的死信息，而是"两天后可以来看" |
| 19 | "路演观摩" | 报名 9/18 22:00 已截止，但"现场仍有余位可接受候补入场"——不是不能去了 |

如果只按"报名截止时间"判断状态，17 会被当成长期有效而沉到列表底部，
04 会被当成已结束直接隐藏，19 会被当成已截止劝退——三条都判断错了。

**处理方式：**

- 把截止时间拆成带**语义标签**的多个节点（"报名截止" vs "网盘提取信息有效期"
  vs "校内意向登记截止" vs "最终作品提交截止"），而不是笼统的一个 deadline；
- 时间精度如实反映：13 号只写了"9月21日截止"没写时间，就标注
  "通知只写了日期，未注明具体时间"，而不是自己补一个 23:59 当事实；
- 为「两个节点的活动」单独保留状态：07、15 在第一个节点过了之后
  仍然显示为可参与，并指出下一个节点是哪天；
- 单独处理"已截止但可候补"（19）和"已结束但有回放"（04）两种中间态，
  不让它们掉进"已结束"的黑洞里。

## 六、运行方式

纯静态前端（原生 HTML / CSS / JavaScript），**不依赖后端、数据库和构建工具**。

```bash
# 直接打开
双击 index.html

# 或起本地服务器（可选，便于手机访问）
node ../serve.js 8080
```

从仓库根目录访问 `/projects/campus-radar/`。详见[仓库根 README](../../README.md)。

**验证**：`node test.js`（在仓库根目录运行），覆盖状态推断、通知合并、
完整度、渲染与日历导出共 68 项检查。

## 七、如果继续开发，最想完善的是

1. **把"合并"做成可配置的规则，而不是靠人工标注。**
   现在 09→01、20→03 的关联关系是写在数据里的。真实场景下需要一个
   相似度 + 时间邻近度的判定，并给出"这条和那条可能是同一件事"的确认入口——
   自动合并出错比不合并更糟，所以需要人来点最后一下。

2. **让发布者自己看到信息的传播效果和缺口。**
   现在的完整度自检只在发布那一刻提示。更理想的是：发布后如果一直没人报名、
   或者被标记了"信息有误"，回访提醒发布者补充信息。

3. **从"这个活动是什么"推进到"这个活动适不适合我"。**
   现在的新生模式是按标签硬筛（零基础、面向全校）。可以结合用户自己填的
   专业、年级、每周可投入时间，给出更贴合的排序。

4. **信息的时效性主动回收。**
   长期招募、待确认场地的信息，超过一定时间后自动提示"这条信息可能已过期，
   请发布者确认"。现在只能靠用户自己判断。
